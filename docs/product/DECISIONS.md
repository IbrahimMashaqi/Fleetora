# Fleetora — Owner Decisions

- **Approved:** 2026-11-25 by the product owner.
- **UX-01: one searchable Combobox pattern for all record pickers (owner, 2026-11-27).** Draft text stays inside the shared `components/ui/combobox`; typing does not apply/clear a selection, navigate, refresh the route or remount the input. Suggestions use approximately 250 ms debounced, authenticated route-handler/fetch reads, server-side Arabic normalization and trusted tenant context. Click/Enter selects; explicit clear clears. List searches update results in place. Short status/action/role enums and free-form creation/contact/address fields are not record pickers.

- **Phase 2 split approved (2026-11-26):** Phase 2a implements the four built-in staff roles (one role per user), explicit Worker-linked driver phone/password identity, suspension and security/offboarding access (BR-042 built-in part, BR-043, BR-035, BR-117, BR-118). Company custom roles (BR-042 custom part) and delegation (BR-044) are deferred to Phase 2b. No driver app is included.
- **Phase 2a staff boundary:** COMPANY_ADMIN retains full company access; OPERATIONS manages parcels, pickups, assignments, drivers and warehouse operations without finance, pricing administration or staff/settings; ACCOUNTANT retains its existing finance permissions and parcel reads; WAREHOUSE handles receipt, warehouse custody and return stages with parcel reads. Pricing, staff/roles and company settings remain COMPANY_ADMIN only. Existing identities are not rewritten or promoted. The existing admin-only adjustment permission is preserved pending clarification of the conflicting accountant-adjustment request.
- **Phase 2a driver identity contract:** Admin/Operations explicitly invites an existing company Worker, never matches by phone/name. Phone/password login uses normalized +970/+972 numbers and the existing throttling/client-source rules. Driver phones are globally unique and accounts link 1:1 to a tenant-checked Worker; existing Workers remain unlinked. Invitation links use HTTPS `/driver/activate#token=...`; hashed, expiring, single-use, revocable tokens; copy/wa.me sharing only. Recovery is an administrator re-invitation. Suspension stops new tasks without removing login or existing obligations; security revocation immediately blocks sessions/login. Offboarding stops new tasks with optional access revocation; final settlement remains deferred.
- **Authority:** these decisions resolve the listed conflicts between the approved sources and the current code. They sit alongside the authority order in [README.md](README.md); they do not add rules beyond those cited.
- **Development activation exception approved (2026-11-27):** Driver, merchant and staff activation links may use HTTP only when backend `NODE_ENV != production` and the URL host is loopback (`localhost`, `127.0.0.1`, `::1`). All other activation origins require HTTPS; production always requires HTTPS. This qualifies the HTTPS-only development limitation above. Tokens remain in the fragment, never the query. The frontend uses server-only `FLEETORA_ACTIVATION_ENV` metadata matching backend `NODE_ENV` because Next's production build mode also serves local Docker development; Compose derives both from `BACKEND_NODE_ENV`. Without that metadata the frontend uses its own `NODE_ENV` and remains HTTPS-only in production.
- **"Docs win"** means the cited approved rules are implemented as written and the current code must be changed in the target phase. Until then, the existing code stays as is.

### OD-15 PR 1 implementation and rollout

- Only platform identity is implemented in PR 1. OD-16..OD-18 company lifecycle, plans, grace and manual payments remain for PR 2/3; OD-19 deferrals remain explicit. Existing company/user/Worker records and credentials are unchanged. Existing legacy PLATFORM_ADMIN users receive no platform staff role automatically; the company-membership authentication foundation is not globally activated.
- Deploy the additive `phase3_platform_identity` migration before using the console or bootstrap. From `backend`, run `npm run build`, then `npm run platform:bootstrap -- --email owner@example.com`; alternatively supply `FLEETORA_PLATFORM_BOOTSTRAP_EMAIL` and omit the argument. Use an email not already attached to another account. Bootstrap sends mail and prints confirmation only, never the activation URL or credentials.
- Before acceptance, rerunning with the same email reuses the single bootstrap invitation and replaces its expiring token, permitting recovery from email failure. A different email is refused once bootstrap is reserved. After acceptance, bootstrap is permanently refused; additional platform staff are invited by a Super Admin. Tokens are hashed, single-use and expire after 48 hours; activation sets the password and creates a companyless platform identity and explicit grant atomically.
- The console is `/platform`, with `/platform/login` and public `/platform/activate#token=...`. All team administration and audit reads require a persisted SUPER_ADMIN; the other roles can read their own platform identity. Company administration and billing endpoints are not introduced in PR 1. Changing role or active state revokes existing platform sessions; the last eligible active Super Admin cannot be removed or demoted.

- Local development mail capture (owner approved): base `docker-compose.yml` starts Mailpit and explicitly selects unauthenticated SMTP at `mailpit:1025` outside production. Read captured activation emails at `http://127.0.0.1:8025`; SMTP is not published on the host. The start batch prints this inbox URL in local mode. Neon mode excludes Mailpit and retains its existing mail configuration. Production ignores the local flag, requires real authenticated SMTP and keeps the existing implicit-TLS transport. Activation tokens/links are never printed by bootstrap or SMTP debug logs.

### OD-11/15/16 — Phase 3 PR 2 implementation and rollout

- Self-registration now explicitly creates PENDING companies. Email verification permits sign-in to the registration-status page; it does not approve the company. A rejected registration shows its reason and allows only a persisted company administrator to edit basic details and resubmit to PENDING. Approval is independent from security suspension.
- SUPER_ADMIN and COMPANY_MANAGER manage companies; SUPPORT reads administrative metadata only; BILLING has no company-directory access. Platform access grants no company operations or customer/financial data. Direct creation reserves an inactive primary administrator atomically, then sends an expiring, hashed, single-use invitation using `/company/activate#token=...` and POST acceptance. Local mail uses the existing Mailpit setup. Authorized invitation reissue revokes earlier unaccepted links; no account is adopted by email matching.
- Security suspension takes the same company lock as operational writes, increments the company access version, clears refresh sessions and disconnects live Fleet connections. Persisted checks also protect HTTP, tickets, telemetry and write transactions; old access tokens remain invalid after reactivation. Reactivation rotates the access version and clears sessions again so grandfathered suspended companies cannot revive pre-migration tokens. Refresh also compares the signed company version inside its locked transaction, closing the race where an in-flight sign-in saves its verifier after suspension. Existing parcels, custody, COD and settlements are preserved. Revision checks reject concurrent/stale lifecycle changes; all lifecycle/profile actions are audited.
- Company administrators edit only company name, phone and address. Approval, suspension, currency and subscription plan remain platform-controlled; company currency transitions remain deferred under OD-02. No writable company id or platform-controlled field is accepted in this profile API.
- Deploy the additive `phase3_companies` migration before this application version. Existing companies become ACTIVE through the additive default, retaining suspension, staff authority, passwords and data; existing primary administrators are not guessed or assigned. No Neon migration or bootstrap is part of this PR. OD-17/18 subscription plans, Legacy assignment, expiry/grace and manual payments remain PR 3; OD-19 deferrals remain unchanged.
